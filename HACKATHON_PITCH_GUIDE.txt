ALERTBUZZER - HACKATHON PITCH GUIDE
===================================

THE ONE-LINE IDEA
-----------------
AlertBuzzer turns a photo or a short report into a trackable safety/maintenance
incident, connecting the person who notices a problem with the people who can
review and resolve it.

THE PROBLEM
-----------
Road damage and campus facility problems are often reported informally. Reports
can lack a precise location or photo evidence, and the reporter may not know
whether anybody reviewed the issue or what happened next.

THE SOLUTION
------------
AlertBuzzer has two clear flows:

1. ROAD ANALYSIS
   - Upload or capture a JPEG/PNG road image.
   - Amazon Rekognition returns general image labels; the prototype applies
     hazard aliases, confidence thresholds, and road-context checks.
   - Show a rule-based risk score/severity, labels, map context, and recent
     analysis history.
   - AWS Polly voice alerts and S3 audio storage are optional integrations.

2. CAMPUS ISSUES
   - Submit classroom/building/facility reports with flexible building, program,
     room, issue, description, priority, optional photo evidence, and a
     responsible-team field.
   - Reports persist in SQLite so the list can be restored after refresh.
   - A password-protected admin portal can review, approve/reject, assign a team,
     and update report status.

The interface also includes separate Road analysis / Campus issues navigation,
responsive mobile layout, dark/light theme, image preview controls, GPS/map
controls, and an API inspector.

SUGGESTED 60-90 SECOND PITCH
---------------------------
"Think about the last time you noticed a pothole or a broken classroom AC.
Usually you take a photo, send a message somewhere, and then have no clear way
to track what happened.

AlertBuzzer creates a simple path from seeing a problem to tracking its review.
For roads, a user uploads or captures an image. AWS Rekognition supplies image
labels, and our prototype turns supported road-context labels into a risk
signal, recent history, and map view. Optional AWS Polly can provide a spoken
alert.

For campus issues, users report a building, department, room, issue, priority,
and optional photo. The report is saved, and an administrator can review it,
assign a responsible team, and move it from Pending to Approved, In Progress,
Resolved, or Rejected.

We are starting with a campus-sized workflow that can be adapted to other
communities. This is a working prototype, not a claim of perfect AI detection:
general-purpose Rekognition can miss potholes, so our next step is testing with
local examples and, if results justify it, evaluating a road-damage model.
AlertBuzzer makes the report and follow-up process visible, even while the
detection capability is improved."

LIVE DEMO ORDER
---------------
1. Start backend and frontend before judges arrive; confirm backend indicator
   says connected. Keep both terminal windows available.
2. Open Campus issues. Show a short report with a real campus block, room,
   problem, priority, and (if time/network allows) one photo.
3. Show the new report in the submitted list and point out Pending.
4. Open Admin, sign in using the locally configured demo password, open the
   report, assign the team, set Approved or In Progress, and save.
5. Return to Campus issues and refresh/show the changed status.
6. Switch to Road analysis. Upload one pre-tested JPEG/PNG and explain the
   displayed labels and risk score as a signal, not a calibrated probability.
7. Briefly show the map/history and voice alert if AWS Polly/S3 work reliably.
   If any optional service is down, state that clearly and continue.
8. End with the two-roadmap items below, rather than trying to demo every
   setting or every edge case.

HONEST LIMITATIONS - SAY THESE IF ASKED
---------------------------------------
- The default model is Amazon Rekognition's general-purpose label service; it
  is not a trained pothole detector and can miss damage or mislabel images.
- The risk score is a prototype heuristic based on labels and thresholds. It is
  not a measured accident probability or an official engineering assessment.
- Rekognition Custom Labels support is optional, but no trained road-damage
  model is currently deployed/configured.
- Campus reports are saved and can be manually reviewed in the admin portal.
  The prototype does not automatically notify campus staff or guarantee repair.
- Photo evidence is stored locally by this prototype; this is not yet a
  production multi-campus storage/privacy architecture.
- Do not claim government deployment readiness. Say the workflow could be
  adapted for municipal use after validation, access-control, hosting,
  notification, retention, and operational requirements are addressed.

LIKELY JUDGE QUESTIONS
----------------------
Q: Is the AI detecting potholes accurately?
A: "It uses Rekognition general labels and our rule-based context checks. That
   is useful for demonstrating the pipeline, but it is not a dedicated trained
   pothole model. We are measuring it against real local images before making
   accuracy claims."

Q: What does the risk score mean?
A: "It is a heuristic priority signal derived from detected labels, not an
   accident probability. It helps triage a prototype report; a validated model
   and operational calibration would be required for real safety decisions."

Q: What happens after a campus report is submitted?
A: "It is saved as Pending. An authenticated admin can review it, set a status,
   and record the responsible team. Automatic staff notification is future
   work."

Q: Why combine roads and campus maintenance?
A: "They share the same product problem: people see a physical issue, need to
   attach evidence and location, and need a visible path to review. We keep the
   road-image analysis and campus-report flows separate while reusing the
   incident workflow."

Q: Can the government use it?
A: "The idea could be adapted to municipal workflows, but this prototype is not
   government-ready. It would need a validated detector, official routing,
   managed identity, secure hosted evidence, privacy/retention rules, and
   integration with actual maintenance teams."

Q: What is innovative here if reporting apps exist?
A: "The prototype brings image-assisted road triage and a human-reviewed
   facilities workflow into one demonstrable incident lifecycle. The value is
   not a claim that every component is new; it is a focused, testable workflow
   that links evidence, location, priority, review, and status."

Q: What would you build next?
A: "First collect consented local examples and measure false positives and
   misses. Then improve the model only if evaluation shows the benefit, add
   notifications and better campus routing, and validate the operational
   workflow with actual users."

TOP-3 PITCHING TIPS
-------------------
- Start with a relatable 10-second story, not the AWS service list.
- Show one complete incident lifecycle: submit -> Pending -> admin review ->
  status updated.
- Let judges see the interface while describing what a user can do.
- Keep the live demo to about 90 seconds; avoid navigating every utility.
- Say "prototype", "heuristic", and "needs validation" when appropriate. Honest
  limitations plus a clear validation plan build more trust than unsupported
  accuracy claims.
- If the live network fails, use a pre-tested local example only if it is
  clearly marked as a demo; never imply it is a fresh AWS analysis.
- End with a concise ask: pilot the reporting workflow with one campus block
  and evaluate whether it reduces time-to-review.

BEFORE THE FINAL
----------------
- Confirm both servers are running and the backend URL is correct.
- Confirm AWS credentials are active without displaying or sharing them.
- Test one road image and one campus report end-to-end.
- Configure and test the admin password locally; never put it in slides,
  screenshots, source control, or chat.
- Confirm camera permission, map connectivity, and Polly/S3 if using them.
- Have screenshots or a short recorded fallback ready; label them as screenshots,
  not live results.
- Remove any temporary test-only reports before presenting live data.
- Do not promise a top-three result; focus on a clear story, a reliable demo,
  a real user problem, and honest evidence.
